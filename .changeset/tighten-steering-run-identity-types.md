Tightened two exported steering types (AB-236, closing gaps AB-221's review found in AB-203's exported shapes), and propagated the tightening through every consumer of `RunOptions`:

- `SteeringCommandFailure` is now a discriminated union on `reason`, one member per reason, instead of one interface with an optional field. The `'superseded-by'` member requires `readonly supersededBy: string`; every other member carries `supersededBy?: never`, so a literal _or non-literal_ value supplying a real `supersededBy` alongside a different reason — a builder return, an intermediate variable, anything TypeScript's literal-only excess-property check doesn't see — or omitting it alongside `'superseded-by'`, is now a compile error instead of a documented-only invariant. This package's `exactOptionalPropertyTypes: false` still lets a literal explicit `supersededBy: undefined` through (the same caveat `SteeringRequestedValue`'s `override?: never`/`policyRef?: never` pair already carries) — behaviorally indistinguishable from omitting the field, so not a real gap.
- `RunOptions` is now a discriminated pair (a conditional-type variant, not two independently-optional fields) on `runId`/`steering`: either both are absent/optional, or `runId` is required and `steering` (present or not) may hold a `SteeringGate`. The pairing is one-directional — an actually-present `SteeringGate` requires `runId`; plenty of callers legitimately supply `runId` with no steering intention at all. `runStep`'s AB-221 `steering.applied` dispatch stamps `SteeringEffectiveState.appliedAtRunId` from `runId` and has no honest fallback when it's absent — a steering-enabled run with no `runId` used to silently never fire that event. AB-67's decision record names two ways to close this: make `runId` required whenever `steering` is set, or synthesize one through the identifier seam AB-214 introduces. **AB-214 has not merged**, so this release takes the type-level option. `RunOptionsBase` (every `RunOptions` field except this pair) is now a separate exported interface, following AB-16's `CreateAgentOptions`/`CreateAgentOptionsBase` precedent, so a consumer that previously wrote `interface X extends RunOptions` still has a supported extension point. `runId` and `steering` are both `readonly`, so a helper holding an already-valid `RunOptions` cannot mutate either field independently back into an invalid combination. `SteeringCommandFailure`'s equivalent migration is an intersection — `type LoggedFailure = SteeringCommandFailure & { traceId: string }` — since an `interface` cannot `extend` a type containing a union.

**Migration:**

- A caller constructing a steering-enabled `RunOptions` literal — directly, or through `executeLoop`, `buildStepDeps`, or `createActiveRun` — must now also supply `runId`. A run with no `steering` is unaffected; `runId` stays optional there, exactly as before.
- A derived options type built with `Omit<RunOptions, ...>` or `Partial<RunOptions>` no longer preserves the `runId`/`steering` pairing (both are non-distributive over a union) — use a distributive `Omit`/`Pick` if a derived type still needs to enforce it. `SessionRunOptions` and `SchedulerRunOptions` (both exported) now do this, and both additionally **omit `runId` entirely**: a session's and a scheduled task's `runId` are always derived internally (`deriveRunId`/`SCHEDULER_RUN_ID_PREFIX`-prefixed ids) and stamped in, overwriting anything a caller supplies — so neither type requires or even accepts a caller-supplied `runId` any more. A caller who was passing one through either type should drop it; it was already being discarded.
- The **in-memory scheduler dispatch path** (`Scheduler.dispatch`/`submitImmediate`'s non-durable branch) now derives and stamps a `${SCHEDULER_RUN_ID_PREFIX}<taskId>-<requeueAttempt>` run id on every run it starts, where it previously left `RunOptions.runId` `undefined` unless the caller supplied one. This is an observable runtime change, not type-only: curated `tool.*` bubble events for an in-memory scheduled run now carry that derived id instead of falling back to `runId: ''` inside `createActiveRun`. The requeue-attempt suffix matters: a `background`/`ambient` in-memory task preempted mid-run is requeued as the same `QueuedTask` and restarted from scratch (never resumed the way a suspended durable one is), so `taskId` alone repeats across attempts — the suffix keeps each restart's identity distinct. The durable scheduler path already had an equivalent derived id (with its own retry counter) for its preemption/resume bookkeeping; this brings the in-memory path to parity and is what makes `SchedulerRunOptions` omitting `runId` sound in both branches.
- `CreateHeartbeatOptions.createHeartbeatRun` (`create-heartbeat.ts`) is now typed `() => SchedulerRunOptions | Promise<SchedulerRunOptions>` instead of `RunOptions`, matching `create-durable-heartbeat.ts`'s existing shape — a caller configuring a steering-enabled heartbeat no longer needs to invent a throwaway `runId`.

**Not addressed in this release:** `createActiveRun`'s own durable-routing entry point (`create-run.ts`) still requires `options.runId` on a steering-enabled `RunOptions` even when durable routing separately supplies the authoritative run identity (`DurableRunRouting.runId`), which the durable driver already uses instead. Applying the same derive-and-omit pattern there is out of scope for this release — `create-run.ts` was under concurrent edit by another in-flight change at the time of this release and is left untouched; a caller can still supply the (currently redundant but harmless) `runId` explicitly today.

When AB-214 merges, `createActiveRun` may instead synthesize a `runId` for a steering-enabled run with none supplied, which could relax the `RunOptions` constraint further — a separate, later decision, not made here.
