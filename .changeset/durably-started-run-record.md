`ActiveRun` gains a new optional field, `durablyStarted?: Promise<void>` (AB-361), so a caller on the durable branch can await the moment this run's initial workflow record is durably committed, distinct from `result` (the run's own completion). It settles with the exact write `driveDurableRun`'s `context.engine.start(...)` performs in `durable/active-run-adapter.ts`: `createDurableActiveRun` resolves it once that call commits (or immediately, on a path — an `onRunStart` hook error, or an abort delivered before the deferred microtask fires — that never durably launches at all, since there is then no write to await), and rejects on any pre-commit failure: `engine.start` itself rejecting, or a caller-supplied `onServices` callback throwing before `engine.start` is even reached. `reattachDurableActiveRun` sets it to an already-resolved promise: a recovered run's durable record predates the reattaching process. The in-memory branch (`createActiveRun` with no `durable` routing) leaves it `undefined` — there is no durable write, and this is itself the proof that the in-memory branch's timing is unaffected.

This closes a gap in the started-work control contract (AB-34/AB-15): bureau's `createRunFromRequest` previously resolved a durable run's identifier to its caller as soon as the session's `lastRunStatus: 'running'` write landed — several microtasks before `engine.start`'s own write. A caller that received the run id and then crashed before that later write committed could leave a run recovery could not see. `createRunFromRequest` now awaits `activeRun.durablyStarted` (guarded by `runtime.durable`, so the in-memory branch gains no extra await) immediately before returning, so an acknowledged durable run is genuinely durable — a process killed at any point after the caller holds the identifier can recover it.

`ActiveRun.result` never rejects raw on a pre-`engine.start` failure (review fix, PRRT_kwDORvupsc6gWc39/PRRT_kwDORvupsc6gWb3a): both failure sources above are routed through the SAME `makeErrorResult` helper the pre-existing `onRunStart`-failure branch already used, so `result` resolves with a `finishReason: 'error'` `RunResult` and a `run.completed`/`RunCompletedEvent` genuinely fires. A caller like bureau's `createRunFromRequest`, which relies entirely on that terminal event to unregister the run and persist its terminal session state, is not left with a permanently-registered "leaked" run and a session stuck at `lastRunStatus: 'running'` just because it also awaits `durablyStarted` (which still rejects, independently, with the same error).

**Migration:** no action needed for a caller that only reads `ActiveRun.result`/`closed()`/the event surface — `result` now always resolves except in the pre-existing abort/dispose cases, unchanged from before. A caller building its own durable-branch composition on top of `createDurableActiveRun` (bureau's own `createRunFromRequest` is the first-party example) should await `durablyStarted` before treating a returned run identifier as durably acknowledged; a caller that never reads the field is unaffected — a rejecting `durablyStarted` is caught internally and never surfaces as an unhandled rejection for a caller that does not await it.
