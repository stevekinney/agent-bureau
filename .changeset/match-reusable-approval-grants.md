Match reusable approval grants ahead of capability approval, and add `Toolbox.issueGrant`/`revokeGrant`/`listGrants` (AB-46, AB-346; builds on AB-345's grant type and `GrantStateStore`).

`createToolbox`'s `mergePolicies`-composed `beforeExecute` now checks for a matching reusable approval grant ahead of `evaluateCapabilityApproval`'s `ask` outcome: when the two-axis capability policy would otherwise pause a call for approval, a grant whose `principalId`/`tenantId`/`ownerId`/`agentId`/`toolName`/`resourcePattern`/`argumentConstraints`/`policyRevision` all match the current call and its `requestContext.authority`, that is unrevoked, unexpired, has `usesRemaining > 0`, and whose signature still verifies, lets the call execute without prompting for approval. A match decrements `usesRemaining` by one and emits a new `'grant.used'` toolbox event (`ToolboxGrantUsedEvent`) recording the grant id, the matched tool call, the deciding principal, and the grant's remaining uses — the audit entry the decision record calls for. A grant failing any check — no match, expired, revoked, exhausted, a stale `policyRevision`, or an invalid signature — is treated as absent, never an implicit deny or approve: the ordinary `ask` pipeline runs unchanged. A capability `deny` remains terminal and is never overridden by a grant, since `evaluateCapabilityApproval` is still evaluated first.

New `ToolboxOptions.grantStateStore` threads a `GrantStateStore` through a toolbox exactly like `approvalStateStore` already threads `ApprovalStateStore`; it defaults to a process-local store only when `approvalSecret` is configured, since a grant is only ever trusted once its signature verifies. `Toolbox` gains three new methods: `issueGrant(input)` mints and signs a `ReusableApprovalGrant` (id and `issuedAt` from the toolbox's own nonce generator and clock, `usesRemaining` initialized to `maxUses`, `policyRevision` defaulted to the toolbox's current revision), `revokeGrant(id)` (idempotent), and `listGrants(filter?)` (optionally narrowed by `principalId`/`agentId`/`toolName`). All three throw when the toolbox has no `approvalSecret`/grant state store configured.

`resourcePattern` matches a glob-style pattern against a caller-declared `resource` field in the tool's arguments (absent pattern matches any resource; a pattern with no `resource` field never matches). `argumentConstraints` is plain JSON data — never a live Zod schema instance, since a grant's signature is computed over its JSON-serialized fields — matched by deep equality per declared key against the call's arguments.
